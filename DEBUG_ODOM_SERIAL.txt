PHẦN A — TEST TẦNG SERIAL + FIRMWARE (KHÔNG CẦN ROS2)
============================================================================
=> Mục đích: xác nhận Arduino Mega CÓ đang gửi dữ liệu hall lên PC hay không.
=> Nếu bước này FAIL thì MỌI bước sau đều vô nghĩa.

A1) Kiểm tra máy tính có "thấy" cổng không
    ls -l /dev/ttyACM0
    - Có hiện /dev/ttyACM0  => cổng OK, sang A2.
    - KHÔNG có:
        + Cắm lại cáp USB (ưu tiên cổng USB trực tiếp, không qua hub).
        + Thử lệnh: ls -l /dev/ttyACM* /dev/ttyUSB*   (xem có cổng khác không)
        + Nếu vẫn không có -> lỗi cáp / board / driver. Dừng lại.

A2) Đọc TRỰC TIẾP dữ liệu thô (PHẢI TẮT mọi node ROS2 trước!)
    sudo cat /dev/ttyACM0
    Sau đó DÙNG TAY QUAY BÁNH XE.
    - Kết quả MONG ĐỢI: màn hình chạy liên tục ~20 dòng/giây dạng:
            0,0        (khi xe đứng yên)
            12,13      (khi quay bánh, con số TĂNG DẦN)
            ...
      Ghi chú: nếu quay ngược chiều, số có thể GIẢM/XUỐNG ÂM (bình thường).
    - Nếu THẤY đúng như trên => Serial + Firmware TỐT. Nhấn Ctrl+C, sang PHẦN B.
    - Nếu KHÔNG THẤY gì hoặc thấy RÁC lộn xộn:
        + Nạp LẠI firmware ARDUINO_MEGA.ino cho Mega (xác nhận baud 115200
          trong Serial Monitor để test).
        + Kiểm tra cáp USB (cáp data chứ không phải cáp sạc!).
        + Thử nút RESET trên Mega rồi cat lại.
        + Mở Serial Monitor của Arduino IDE (115200) KHÔNG nối cùng lúc với
          cat. Nếu Serial Monitor thấy data mà cat không thấy -> vấn đề là
          quyền/cổng trên Linux, không phải firmware.

A3) [TÙY CHỌN] Đo xem Arduino có "treo" không (thử bằng tay cầm)
    Bật nguồn motor riêng, dùng tay cầm PS điều khiển xe.
    Đồng thời mở Serial Monitor 115200.
    - Nếu xe chạy được (ESP32->Mega -> motor) nghĩa là firmware chạy tốt,
      vậy vấn đề chỉ nằm ở khâu gửi serial lên PC hoặc node đọc.

  [ ] A3: xe chạy được bằng tay cầm
  => Nếu A2 OK thì lỗi KHÔNG nằm ở serial/firmware.

PHẦN B — TEST NODE ĐỌC SERIAL ĐƠN LẺ (CHƯA BẬT SLAM/LIDAR)
============================================================================
=> Mục đích: xác nhận node C++ arduino_odom_node CÓ nhận được data và
              CÓ publish /odom hay không. Tách riêng để không bị nhiễu
              bởi lidar/slam/rviz.

B1) Xem log khởi động node (PHÁT HIỆN LỖI MỞ CỔNG — rất hay gặp!)
    ros2 run hall_reader_cpp arduino_odom_node
    QUAN SÁT KỸ:
    - Nếu in ra:
          "Không thể mở cổng Serial ESP32/Arduino!"
      => LỖI MỞ CỔNG. Node vẫn "sống" nhưng KHÔNG BAO GIỜ publish data
         (đây chính là lý do "/odom có trên topic list nhưng không có data").
      => Xử lý: (a) đã chạy "sudo chmod 666 /dev/ttyACM0" chưa?
                (b) có node nào khác đang giữ cổng không? (xem B2)
                (c) cổng có đúng /dev/ttyACM0 không?
    - Nếu in ra "Đã khởi động Node Odom C++ siêu tốc!" => mở cổng OK.

B2) Kiểm tra xem CÓ node nào khác đang giữ /dev/ttyACM0 không
    (quan trọng: cmd_vel_to_serial.py cũng mở cổng này — chạy 2 cái cùng
     lúc sẽ tranh chấp!)
    ps aux | grep -E "arduino_odom|cmd_vel_to_serial|joy"
    - Nếu thấy cmd_vel_to_serial hoặc joy_to_serial đang chạy -> kill nó:
         pkill -f cmd_vel_to_serial
         pkill -f joy_to_serial
    - Nếu thấy arduino_odom_node chạy nhiều bản -> kill bớt:
         pkill -f arduino_odom_node

B3) MỞ 1 terminal mới, đo TẦN SUẤT /odom:
    ros2 topic hz /odom
    - MONG ĐỢI: ~20 Hz (vì Arduino gửi 20 lần/giây).
    - Nếu ~20Hz  => node nhận data, publish tốt. Sang B4 để xem giá trị.
    - Nếu 0.0 Hz / "no new messages" => node KHÔNG nhận được data.
      => Quay lại PHẦN A (chắc chắn cat OK khi tắt node), kiểm lại việc
         mở cổng (B1), quyền, và xem có tranh chấp cổng không (B2).

B4) MỞ terminal khác, xem GIÁ TRỊ /odom có đổi khi quay bánh không:
    ros2 topic echo /odom
    Quay bánh xe bằng tay, quan sát:
    - pose.pose.position.x  và  pose.pose.orientation.z  (góc quay)
      phải THAY ĐỔI khi bánh quay.
    - Nếu x/y/theta đổi => NODE ODOM TỐT. Sang PHẦN C.
    - Nếu hz ~20 mà giá trị không đổi dù quay bánh:
      => nghi ngờ: (a) hai bánh quay cùng lúc nhưng delta = 0 (quay ngược
         chiều nhau triệt tiêu), (b) hệ số PULSES_PER_REV/chiều quá nhỏ.
      => Thử quay CHỈ 1 bên bánh phải rồi 1 bên bánh trái, xem có đổi không.
      => Xem PHẦN D (các thông số) để kiểm lại.

PHẦN C — TEST TOÀN BỘ TF (vì SLAM cần TF, không chỉ topic odom)
============================================================================
=> Mục đích: xác nhận chuỗi TF từ odom tới laser_frame là LIÊN TỤC.
   SLAM vẽ map KHÔNG ĐƯỢC nếu thiếu bất kỳ mắt xích TF nào.

C1) Kiểm tra TF odom -> base_footprint (do node odom publish):
    ros2 run tf2_ros tf2_echo odom base_footprint
    - MONG ĐỢI: cập nhật liên tục, translation thay đổi khi quay bánh.
    - Nếu "Could not transform" => node odom chưa publish TF (xem B).

C2) Chạy LAUNCH ĐẦY ĐỦ và kiểm tra toàn bộ cây TF:
    ros2 launch my_robot_description real_mapping.launch.py
    (mở terminal khác:)
    ros2 run tf2_ros view_frames
    Mở file frames.pdf vừa tạo ra, kiểm tra chuỗi:
        map -> odom -> base_footprint -> base_link -> laser_frame
    - Thiếu "map"         => SLAM chưa chạy / chưa tạo map.
    - Thiếu "odom->..."   => node odom chưa publish TF.
    - Thiếu laser_frame   => sllidar_node chưa chạy / static TF sai.
    - Dòng nào đứt thì xử lý đúng node đó.

C3) Kiểm tra các topic quan trọng khi đang chạy launch:
    ros2 topic list
    Cần thấy ít nhất:
        /odom          (odom node)
        /scan          (sllidar_node raw)
        /map, /map_updates   (slam_toolbox)
        /robot_description
    - Xem topic nào có data:
        ros2 topic hz /scan
        ros2 topic hz /odom
        ros2 topic hz /map_updates      (có data = SLAM đang xử lý)
    - Nếu /scan có data mà /odom KHÔNG có => SLAM không thể map được
      vì thiếu odometry -> lỗi nằm ở odom/serial (quay lại B/A).
    - Nếu /scan KHÔNG có data => lỗi lidar (cổng /dev/ttyUSB0, nguồn,
      motor lidar quay chưa) -> KHÔNG liên quan odom bạn đang debug.

PHẦN D — NẾU DATA CÓ TỚI NHƯNG ODOM "SAI" (chạy lệch/giật/không đúng)
============================================================================
=> Mục đích: khi chắc chắn data tới ổn (B+C OK) nhưng bản đồ/đường đi
   không khớp thực tế, kiểm các thông số & lỗi tiềm ẩn trong code.

D1) KIỂM TRA CÁC HẰNG SỐ VẬT LÝ (phải đo thực tế, đang hard-code):
    File: hall_reader_cpp/src/arduino_odom_node.cpp (khoảng dòng 45-47)
        PULSES_PER_REV = 330   <- số XUNG HALL cho 1 VÒNG BÁNH XE
                                   (đếm thực tế: quay bánh đúng 1 vòng,
                                    xem số hall tăng bao nhiêu -> ghi lại)
        WHEEL_RADIUS   = 0.065 <- bán kính bánh xe (mét) - ĐO LẠI
        WHEEL_BASE     = 0.25  <- khoảng cách 2 tâm bánh (mét) - ĐO LẠI
    LƯU Ý QUAN TRỌNG: PULSES_PER_REV phải tính cho CẢ motor + hộp giảm tốc.
    Nếu sai hệ số này, xe đi 1m nhưng odom báo 0.7m hoặc 1.4m (chạy thẳng
    thì lệch tỉ lệ; chạy vòng thì quay sai góc -> map méo).

D2) LƯU Ý LỖI ĐẾM XUNG TRONG FIRMWARE (debounce nằm SAU khi đếm):
    File: CONTROL WITH PLAYSTATION_SLAM/ARDUINO_MEGA/ARDUINO_MEGA.ino
          hàm intrupt_L()/intrupt_R() (dòng ~182, ~200)
    Hiện tại: ngắt kiểu CHANGE (chạy CẢ sườn lên + xuống) và lệnh
    total_pulses_*++ nằm TRƯỚC khối lọc "tic-tac<5" -> nếu hall bị
    nhiễu/rung sẽ ĐẾM DƯ -> odom chạy xa hơn thực tế, bị "giật".
    => Nếu nghi ngờ nhiễu: có thể cần đổi sang chỉ đếm 1 sườn (RISING)
       HOẶC chuyển debounce lên trước lệnh đếm. (Cần sửa firmware + nạp lại.)

D3) TEST "ĐI THẲNG 1m" ĐỂ HIỆU CHỈNH (calibration đơn giản):
    1. Đánh dấu vị trí xe, cho xe đi thẳng (bằng tay cầm / lệnh) 1 khoảng
       đã đo, VD 1 mét.
    2. Đọc lại:
         ros2 topic echo /odom --once
       lấy pose.pose.position.x.
    3. Nếu xe đi 1.0m thật mà odom báo 0.8m:
         -> hệ số dist_per_pulse đang NHỎ => giảm PULSES_PER_REV
            (hoặc tăng WHEEL_RADIUS) theo tỉ lệ 1.0/0.8.
       Nếu odom báo 1.2m: làm ngược lại.
    Công thức: PULSES_PER_REV_mới = PULSES_PER_REV_cũ * (odom_báo / thực_tế)

D4) TEST QUAY 90 ĐỘ (hiệu chỉnh WHEEL_BASE):
    1. Cho xe quay tại chỗ đủ 90 độ (đo bằng thước/giác kế).
    2. Đọc orientation.z trong /odom (góc quay).
       - odom quay > 90 -> WHEEL_BASE đang QUÁ NHỎ -> tăng lên.
       - odom quay < 90 -> WHEEL_BASE đang QUÁ LỚN -> giảm xuống.
       (Vì delta_theta = (dist_R - dist_L) / wheel_base)

D5) KIỂM TRA DẤU/CHIỀU 2 BÁNH (nếu đi thẳng nhưng odom xoay vòng):
    - Nếu 2 bánh đếm ngược dấu nhau (1 bánh tăng, 1 bánh giảm khi đi
      thẳng) thì delta_L và delta_R trái dấu -> theta quay liên tục.
      => Kiểm tra chiều quay encoder/định nghĩa DIR_L/DIR_R trong firmware
         có khớp với hướng bánh thực tế không.
